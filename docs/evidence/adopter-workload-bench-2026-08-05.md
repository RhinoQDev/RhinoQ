# Adopter-shaped workload benchmark

Run 2026-08-05 by `tests/postgres/adopter_workload_bench_test.go` against
`postgres:16-alpine`, connecting as the unprivileged `rhinoq_app` role with
row-level security in force.

```
goos: windows  goarch: amd64
cpu: AMD Ryzen 5 5600 6-Core Processor
go test -run '^$' -bench BenchmarkAdopter -benchtime 200x .
```

## Why this shape

`docs/design-partners.md` defines seat A as an "import, export, media or AI
batch with at least 100 items" and states the proof RhinoQ must produce:
*Task summary polling stays bounded*. That is a claim about how cost behaves as
fan-out grows, so it can only be checked by running the same operation at
several fan-out sizes. One number at one size cannot falsify it.

## Result

| Operation | fan-out 100 | fan-out 1,000 | fan-out 5,000 |
|---|---|---|---|
| `GetTaskSummary` | 793 µs | 819 µs | 797 µs |
| `ListTaskExecutions` (page of 50) | 1.90 ms | 1.86 ms | 1.92 ms |

Both are flat. Summary polling is bounded, as claimed.

## What the first run found

The page was **not** bounded before migration 028:

| Operation | fan-out 100 | fan-out 1,000 | fan-out 5,000 |
|---|---|---|---|
| `ListTaskExecutions` (page of 50) | 2.04 ms | 2.86 ms | 6.84 ms |

A page of fifty rows cost 3.4× more because the Task had more rows elsewhere.
The keyset pagination was correct throughout — rows could not shift between
pages — but `rhinoq_task_executions` had no index matching the `(created_at,
id)` order, so PostgreSQL read every Execution of the Task and top-N sorted it.

Two things were needed, and finding only the first produced a wrong conclusion:

1. migration 028 adds `(task_id, created_at, id)`;
2. the table has to have been analysed. With stale statistics the planner
   estimated twelve matching rows, chose a bitmap scan — which returns no
   order — and sorted all five thousand anyway, *using the new index to do it*.

Isolated plan cost for the page at fan-out 5,000: 4.218 ms reading 5,000 rows
before, 0.137 ms reading 51 rows and 14 buffers after.

Autovacuum keeps statistics current in a running deployment, so the bad plan is
mainly a hazard immediately after a bulk import — which is exactly when a batch
job creates thousands of Executions and somebody opens the page to watch them.

## What these numbers are not

One machine, one PostgreSQL container, synthetic rows generated by
`generate_series`. They are a regression tripwire for this repository. The
benchmark against a real adopter workload named in `docs/adoption-gap.md`
still requires a real adopter, and nothing here substitutes for it.
